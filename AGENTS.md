# Project rules

Subdirectories may have their own `AGENTS.md` (e.g. `src/features/ops/`); read it before changing files there.

- Active screens live in `src/features/ops/`; `src/pages/Index.tsx` keeps legacy prototype screens (incidents, map, GPS) unreachable but intact — preserve, don't extend.
- Staffing rules (missing/unallocated/status, time zones, CSV) are pure functions in `src/lib/roster.ts`, tested in `roster.test.ts`.
- Roster slots keep immutable `original_*` columns (DB trigger); only approved variations change `current_*`, via `approve_variation` (atomic, applied once). Approval is the `approve_variations` permission.
- Attendance writes go through RPCs (`manager_sign_on`, `allocate_guard`, `sign_off_attendance`); unique partial indexes stop double-counting. Guards never sign themselves on (`guard_sign_on` revoked); the portal shows only the guard pass, and "My shift" is the slot of the guard's open attendance (`guard_on_slot()` policies), never `assigned_guard_id`.
- Every guard belongs to a provider: self-registration picks one from `list_signup_providers()`; poster `?provider=<id>` preselects it.
- Sign-off is only by `auto_sign_off_due()` (5-minute cron, latest `current_end`); `sign_off_attendance` is a Super Admin override; no UI sign-off buttons. `roster_slot_sync_auto_sign_off` moves sign-offs when `current_end` changes on a finished shift.
- SMS goes through Tall Bob, one account per event: `event_sms_settings` (no secrets) → `sms_credentials` (AES-GCM ciphertext keyed by `SMS_CREDENTIALS_KEY`, service-role only). The message's `event_id` picks the account via `checkEventAccount`/`resolveEventAccount` in `supabase/functions/_shared/sms-core.ts` (pure, shared with the app via `src/lib/sms.ts`, tested in `sms.test.ts`); never fall back to another event's account, and refuse unless enabled + tested (`connected`).
- Only edge functions write SMS rows: `send-sms` (manual; scope + `client_key` idempotency), `sms-dispatch` (input-less, wake-on-insert for automatic `pending` alerts, no cron), `sms-settings` (manage_sms: save/test, registers webhooks), `tallbob-webhook` (per-account bearer token hash, events deduped by `provider_event_id`, statuses only move forward via `mergeDeliveryStatus`). `sms_recipients.status` is the delivery status.
- Costs live only in `roster_slot_costs`/`variation_costs` (RLS `can_view_costs()`), never on tables non-admins read; `variations_compute_cost` trigger prices requests.
- Roster uploads read CSV values as text and convert Excel dates to ISO text, so dates never parse as US month/day.
- Roster positions are never pre-assigned to named guards; UI/import/export ignore `assigned_guard_*`. Guards link only through attendance, made at the Sign-in desk via `manager_sign_on` (checks contractor access, double sign-on, filled positions).
- A multi-shift variation request is one `variations` row per shift sharing `group_id` (null if single), so pricing/approval stay per shift; UI bundles via `groupVariations`/`requestStatus` and acts via `*_variation_group` RPCs.
- Access = one user type (`user_roles`) per user; permissions ticked per type in `role_permissions` (`user_permissions` deprecated). `has_permission()` (Super Admin always true) is mirrored by `hasPermission`/`USER_TYPES`/`PERMISSIONS` in `roster.ts`. Actions are enforced in DB. Security types are contractor-scoped via `contractor_members`; event-wide reads use `is_event_staff()`. Never use `USING (true)` reads: `role_permissions` is readable for your own type (managers see all), providers via `can_read_contractor()`, location settings via `can_read_event_location_settings()`.
- Links sent to other people (invites, guard sign-up QR/poster, copied logins) use `shareableOrigin()` in `src/lib/publicUrl.ts`, and `create-user` only accepts invite redirects on the live domain, because editor previews are private to the builder.
- Accounts are created only by the `create-user` edge function (invite email → `/set-password`, or temp password), enforcing the same rule as `addableUserTypes`; removed only by `delete-user` (deletes the login, then profile/roles/memberships; history keeps stored names), enforcing the same rule as `canRemoveUser`.
- Variation staff alerts are queued by statement-level triggers on `variations` → `queue_variation_staff_alert`: new requests alert the provider's acknowledgers (approvers if none); approvers are alerted once nothing in the request awaits acknowledgement. Recipients come from `variation_alert_recipients()` (profiles.phone/email). Each alert writes SMS rows plus one `staff_email_alerts` row per emailed recipient.
- Database changes are SQL files in `supabase/migrations/` (timestamped, applied in order by `supabase db push`). Never hard-code a project URL or key in SQL: wake calls use `edge_function_url()` / `edge_function_headers()`, which read the Vault secrets `project_url` and `anon_key`.
- Email goes through Resend via `supabase/functions/_shared/email.ts` (`RESEND_API_KEY`, optional `EMAIL_FROM`). Login emails use the Supabase Send Email hook (`auth-email-hook`, verified with `SEND_EMAIL_HOOK_SECRET`); staff alerts use `sendTemplateEmail`.
- Alert emails send wake-on-enqueue: an insert trigger pings the input-less `send-staff-alerts` function (claims rows, one email each, idempotency key = row id); a 15-minute retry cron exists only while rows are undelivered and unschedules itself when drained — never add a permanent sweeper.
- Guard location is separate from attendance and never changes sign-on, missing counts, variations or pay. Coordinates are written only by `submit_guard_location` (identity/event/contractor from server records; checks open attendance, consent, cutoff = slot `current_end`, ordering, throttle). Latest-location only: sessions close and coordinates are purged on sign-off/expiry/stop via triggers and `auto_sign_off_due`. Sharing starts only from the guard's own phone after recorded consent (`guard_location_consents`).
- Demo roster: `DEMO-*` shift refs in Summer Stadium Festival 2026 roll forward by whole days via `roll_demo_shifts()` (called from `auto_sign_off_due`, no extra cron), so the demo event always has live and upcoming shifts.
